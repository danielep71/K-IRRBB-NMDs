## 🎯 Purpose

Establish the project's foundation before developing the application:
architecture, baseline contracts, supported environments, source management
rules, and criteria for demonstrating that a change works. The deliverable
is an organized, auditable repository on which later milestones can build
the workbook and models.

## 💡 Why it matters

A numerically plausible model is difficult to verify if its data, units,
authoritative source, or tested version are unclear. The foundation makes
these decisions explicit and separates calculations, Excel integration,
and the public interface. A worksheet or import problem can then be
distinguished from an econometric problem, and each correction can be traced.

## 🔗 Dependencies and transition to the next phase

On October 9, 2026, the owner approved moving the template (#5), VBA
import/export (#6), and Excel test harness (#8) to [v0.2.0](v0.2.0.md).
Their acceptance criteria remain mandatory in that phase.

Accepting the baseline contracts does not resolve the methodological
amendments tracked from #26: #32 data, #33 Rates, #34 Stable, #35 sources
and applicability, #36 Decay verification, and #37 model composition. Each
must be accepted before the implementation it affects.

## 🔎 Practical example

A developer must be able to determine where to add a mathematical function,
which inputs it receives, how to expose it to the application, and which
evidence belongs in the PR. The developer must also understand that a
passing Python check does not establish that the function compiles or
produces correct results in Excel.

## 🚧 Delivery boundaries

This milestone did not deliver a workbook, VBA source, or econometric model,
and certifies nothing numerically. Defining the evidence protocol is not the
same as executing it. The repository became public after a separate
distribution review (#42); closing this milestone authorizes no tag, GitHub
Release, or workbook distribution.
