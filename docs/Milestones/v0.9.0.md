# 🧪 v0.9.0 — Release candidate

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/K-IRRBB-NMDs/milestone/9) · [Previous](v0.8.0.md) · [Next →](v1.0.0.md)

## 🎯 Objective

Qualify the complete agreed NMD application for a stable release on one
frozen, identified candidate.

**Why it matters.** Individually tested components do not guarantee an
installable, reproducible final package. Differences in the built workbook,
host configuration or instructions may prevent users from obtaining the
validated outcome. The release candidate ties all evidence to the same source
and the actual artifacts produced from it.

## 📦 Scope

- Freeze features and the candidate: commit, environments to test and
  acceptance criteria; new features reopen scope and evidence.
- Consolidate independent numerical validation, regressions and model
  evidence, and run the complete workflow on the candidate; validation
  already accompanies each model and is not deferred to this phase.
- Verify installation, upgrade, rollback and failure recovery with agreed
  data volumes and performance targets, recording environment and workload
  without introducing undecided thresholds or generalizing from one case.
- Align user and methodology documentation, supported versions and known
  limitations with what was actually tested.
- Recheck candidate provenance, sensitive-material history and licensing and
  distribution requirements.
- Build the workbook reproducibly from the candidate and record its hash.

## 🏁 Exit criteria

- [ ] All required tests pass on the exact candidate, no blocking defect
  remains and accepted limitations are documented.
- [ ] Independent values, tolerances, Excel tests and end-to-end evidence are
  tied to the identified source and artifacts.
- [ ] Installation, upgrade, rollback, failure recovery and agreed performance
  checks have recorded, reproducible results.
- [ ] Supported-host claims match the evidence; unverified environments
  remain explicit.
- [ ] The workbook is built from the candidate, tested and identified by its
  hash, with a repeatable procedure.
- [ ] The distribution review is recorded for the candidate.
- [ ] Any source change after certification reruns the required checks under
  [`RELEASING.md`](../../RELEASING.md).

**Example acceptance case.** A clean candidate checkout allows the workbook to
be built and opened, synthetic data to be loaded, models to be calibrated,
tests and scenarios to be reproduced and reconciled results to be exported.
The evidence package records the commit, Excel host, configuration,
assertions, tolerances and outcomes, and an intentional failure verifies
recovery in the actual package intended for users.

## 🔗 Tracked issues and dependency

No dedicated issues yet: before qualification, create issues for candidate
freeze, the test matrix, packaging, documentation and distribution review,
each with an assignee, a milestone, exactly one priority and acceptance
criteria. Builds on v0.2.0 through [v0.8.0](v0.8.0.md) and their resolved
prerequisites; the [release procedure](../../RELEASING.md) governs the frozen
source, artifacts and subsequent steps.

## 🚫 Not in scope

New features after the freeze, and any automatic authorization to tag,
publish, distribute or change repository visibility; final acceptance belongs
to [v1.0.0](v1.0.0.md).

## 🧪 Release evidence

- Pass `python tools/check.py --ci` and the hosted Repository integrity check
  on the exact candidate.
- Record Windows Excel 64-bit stages 1–6 of
  [`EXCEL_EVIDENCE.md`](../EXCEL_EVIDENCE.md) on the packaged workbook, the
  complete workflow and an intentional failure with recovery.
- Record consolidated independent references, installation, upgrade, rollback
  and performance results.
- Record the candidate SHA, artifact hash, provenance and licensing review,
  limitations and documentation updates.
- Do not tag, publish or merge to `main` without explicit owner authorization.
