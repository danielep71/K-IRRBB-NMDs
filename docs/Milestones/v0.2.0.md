# 📊 v0.2.0 — Workbook, data and Excel tests

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/VBA-IRRBB-Toolkit/milestone/2) · [Previous](v0.1.0.md) · [Next →](v0.3.0.md)

## 🎯 Purpose

Deliver the application's first operational foundation: an Excel workbook
that can be rebuilt from source, a reliable data-loading workflow, and a
test harness that runs inside Excel. This moves the foundation contracts
into working behavior on the agreed host.

## 💡 Why it matters

Later models depend on correct data, reproducible imports, and results
whose validity and freshness are clear. An error in balance loading or
information-availability dates can distort an estimate even when the
formula is correct. A manually assembled workbook without a reproducible
procedure also makes it difficult to identify the code that actually ran.
This milestone controls those risks at their source.

## 🛠️ Activities and deliverables

### 📁 Workbook and worksheet ownership

Create the sanitized, macro-free `.xlsx` template without confidential
metadata. Define sheet names, the intended CodeNames for the VBA
application, input/output areas, and ownership. Proposed sheets include
Readme, Config, Segments, DataSummary, ModelParams, Calibration, Backtesting,
Scenarios, Results, and Checks. Areas reserved for future functions must be
clearly identified: a worksheet name is not evidence that a feature exists.

### 🔄 Source assembly and export

Define and test ordered VBA component import and subsequent export. Verify
names, encoding, line endings, and form resources where present. Handle
VBA project access permissions and import failures without leaving Excel
settings changed. Any cleanup failure must accompany, rather than conceal,
the original failure.

### 🧾 Data import and validation

Load account and market-data CSV files according to the contract: required
fields, dates, units, currencies, segments, duplicates, account histories,
and missing observations. Produce summaries, reconciliations, and
deterministic diagnostics; record origins, data windows, and transformations.
Rejected input must not leave usable partial outputs or previous results
presented as current.

### 🕒 Information availability and Excel tests

Complete #32 before implementing affected transformations: distinguish the
observation date from the date information became available, and distinguish
verified closure, a missing extract, an observation gap, and the end of the
sample. Then deliver a test runner with case identifiers, assertion counts,
outcomes, and explicit handling of FAIL and NOT RUN.

## 🔎 Practical example

A forecast made on March 31 cannot use a May closure learned in June. If
an account disappears from the April extract, the system must distinguish
a closure from missing data. A test changes information learned after
March and checks that predictors available in March remain identical.
Another test loads an invalid CSV after a successful import and verifies
that previous results no longer appear current.

## 🔗 Dependencies

The v0.1.0 architecture, host, and data contracts are required. The logical
sequence is to specify data rules and failure behavior, prepare the
template, build/import the source components, and run tests in the workbook.
Preliminary work on the experimental Decay branch may be reused after
review, but does not itself prove import/export behavior or Excel execution.

## ✅ Completion criteria

- A clean repository checkout can build the workbook using repeatable
  instructions and verify the import/export round trip.
- Valid synthetic data produces the expected summaries and reconciliations;
  invalid input produces controlled errors without misleading usable output.
- Timing, closure, and missing-data cases follow the accepted #32 amendment.
- Compilation, tests, repeated runs, and failure recovery execute in Windows
  Excel and are recorded against the exact commit.
- Unexecuted cases and environment limitations are explicit. Static CI and
  LibreOffice are not presented as substitutes for Excel evidence.
