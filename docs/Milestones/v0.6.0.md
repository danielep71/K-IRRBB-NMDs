# 🔗 v0.6.0 — Integrated calibration and backtesting

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/VBA-IRRBB-Toolkit/milestone/6) · [Previous](v0.5.0.md) · [Next →](v0.7.0.md)

## 🎯 Purpose

Coordinate Rates, Stable, and Decay in one auditable calibration and
backtesting process. Every run must have identifiable, reproducible data,
configuration, time windows, parameters, and results, without introducing
inconsistencies at model boundaries.

## 💡 Why it matters

Three individually correct engines can produce an incorrect integrated
result if they use different populations, currencies, horizons, or parameter
versions. Historical evaluation can also appear successful because it uses
information learned after the forecast date. This milestone controls both
the economic meaning of model composition and the timing of the workflow.

## 🛠️ Activities and deliverables

| Area | Planned work | Useful evidence |
| --- | --- | --- |
| Parameters | Identify and version consistent parameter sets by model, segment, and currency | Each result refers to the set actually used |
| Orchestration | Coordinate inputs, estimation, diagnostics, and component dependencies | Repeatable execution without implicit steps |
| Windows | Separate estimation periods, test periods, and forecast origins | No predictor or fitted coefficient uses future information |
| Backtesting | Compare forecasts and realizations using contract-defined measures | Reconstructible scores and excluded observations |
| Reconciliation | Reconcile balances, remainders, runoff, and any separately modeled inflows | No missing or duplicated amounts |
| Result state | Invalidate results after input/configuration changes or failures | No outdated results presented as current |

Estimated coefficients remain frozen out of sample under the contract.
Recalibration is a new identifiable run, not a hidden adjustment within
the test period.

## 🧩 Central prerequisite: Stable and Decay

#37 must determine whether the models are alternatives, complementary
estimators, or stages in a defined composition. Stable follows existing
balances; Decay describes aggregate balances that include new accounts.
Automatically multiplying their profiles could count the same runoff twice.

Before integrated implementation, accept the populations, units, horizons,
rate linkage, and meaning of each flow. Core/non-core categories must be
consistent with that contract; regulatory constraints remain in their
dedicated layer.

## 🔎 Practical example

A synthetic case separates an estimation window from a subsequent test
window. The system stores parameters from the first window, generates
forecasts at eligible origins, and compares them with observed outcomes.
An independent reference reconstructs the opening balance, runoff,
remaining balance, and any new inflows under #37. Changing information
learned after an origin must not change predictors available at that origin.

## 🔗 Dependencies

The verified engines from [v0.3.0](v0.3.0.md), [v0.4.0](v0.4.0.md), and
[v0.5.0](v0.5.0.md), the v0.2.0 data rules, and the accepted #37 contract
are required. Standalone model validation remains necessary; a successful
integrated test does not replace it.

## ✅ Completion criteria

- A complete case is reproducible from recorded data, settings, model
  versions, and source commit.
- Out-of-sample execution respects information availability and frozen
  parameters; tests detect contamination from future data.
- Amounts reconcile under the contract without counting runoff twice.
- A component failure does not produce an apparently complete overall
  result; diagnostics and cleanup outcomes remain available.
- Independent references and exact-commit Excel execution cover the
  integrated workflow in addition to the standalone tests already delivered.

## 🚧 Boundaries and tracking

This milestone delivers orchestration and historical evaluation. The
complete user workflow belongs to v0.8.0; coordinated scenarios and
applicable constraints belong to v0.7.0.
[#37](https://github.com/danielep71/VBA-IRRBB-Toolkit/issues/37) tracks the
composition prerequisite. Orchestration and backtesting activities must be
detailed in implementation issues before development.
