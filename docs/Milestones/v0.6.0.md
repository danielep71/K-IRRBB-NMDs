# 🔗 v0.6.0 — Integrated calibration and backtesting

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/K-IRRBB-NMDs/milestone/6) · [Previous](v0.5.0.md) · [Next →](v0.7.0.md)

## 🎯 Objective

Coordinate Rates, Stable and Decay in one auditable calibration and
validation workflow, reproducible from recorded inputs, settings and commit,
with frozen out-of-sample parameters and reconciled amounts.

**Why it matters.** Three individually correct engines can produce an
incorrect integrated result if they use different populations, currencies,
horizons or parameter versions. Historical evaluation can also appear
successful because it uses information learned after the forecast date. This
milestone controls both the economic meaning of model composition and the
timing of the workflow.

## 📦 Scope

- Accept the Stable–Decay integration contract in #37 before integration:
  whether the models are alternatives, complementary estimators or stages in a
  defined composition; populations, units, horizons, rate linkage and the
  meaning of each flow. Stable follows existing balances while Decay describes
  aggregate balances that include new accounts, so profiles are not multiplied
  by default and runoff is never counted twice.
- Version consistent parameter sets by model, segment and currency; each
  result refers to the set actually used.
- Orchestrate inputs, estimation, diagnostics and component dependencies per
  segment and currency, without implicit steps.
- Separate estimation windows, test windows and forecast origins;
  coefficients stay frozen out of sample, and recalibration is a new
  identifiable run, not a hidden adjustment within the test period.
- Score forecasts against realizations with contract-defined measures, with
  reconstructible scores and excluded observations.
- Reconcile balances, remainders, runoff and any separately modeled inflows;
  produce diagnostic summaries and run provenance. Core/non-core categories
  follow #37, and regulatory constraints stay in their dedicated layer.
- Invalidate results after input or configuration changes and failed runs.

## 🏁 Exit criteria

- [ ] An end-to-end synthetic case is reproducible from recorded data,
  settings, model versions and source commit.
- [ ] No future data enter predictors or calibration; tests detect
  contamination from information learned after an origin.
- [ ] Cross-model amounts reconcile under #37 without counting runoff twice.
- [ ] A component failure never produces an apparently complete overall
  result; diagnostics and cleanup outcomes remain available.
- [ ] Standalone model results from v0.3.0–v0.5.0 are unchanged.
- [ ] Independent references and exact-commit Windows 64-bit Excel execution
  cover the integrated workflow, in addition to the standalone tests.
- [ ] README, CHANGELOG, `MODEL_CONTRACTS.md`, `VALIDATION_PLAN.md` and this
  guide describe the workflow, windows, scoring and limitations.

**Example acceptance case.** A synthetic case separates an estimation window
from a subsequent test window. The system stores parameters from the first
window, generates forecasts at eligible origins and compares them with
observed outcomes. An independent reference reconstructs the opening
balance, runoff, remaining balance and any new inflows under #37. Changing
information learned after an origin does not change predictors available at
that origin.

  out-of-sample, leakage, invalidation and component-failure runs.

  derivation, reviewer, tolerance and limitations.

  documentation updates.
