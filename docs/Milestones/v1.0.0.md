# 🚀 v1.0.0 — First validated NMD application

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/VBA-IRRBB-Toolkit/milestone/10) · [Previous: v0.9.0](v0.9.0.md)

## 🎯 Purpose

Accept and, with explicit authorization, release the first stable Excel/VBA
application for behavioral modeling of non-maturity deposits. The delivered
product must have clearly identified scope, versions, limitations, and
supporting evidence.

## 💡 Why it matters

A stable version number is a commitment to the content actually delivered.
Users must be able to identify which workbook to use, which source produced
it, which environment was tested, and which operations are supported.
Final acceptance prevents an internal candidate or development folder
from being mistaken for an accepted product.

## 📦 Included deliverables

| Function | Expected outcome within the approved scope |
| --- | --- |
| Data | Controlled import with segmentation, reconciliation, and lineage |
| Decay | Verified estimation and time profiles with explicit assumptions |
| Rates | Calibration, diagnostics, and customer-rate response simulation |
| Stable | Existing-balance survival estimation and consistent aggregation |
| Integrated process | Versioned parameters, historical backtesting, and reproducible results |
| Scenarios and constraints | Consistent paths and verified overlays, separate from the fit |
| Operation and export | Workbook workflow, save/load, and a controlled ALM schema |
| Documentation | Installation, synthetic examples, methodology, versions, and limitations |

The workbook does not require an external numerical engine for the planned
calculations. Any offline tools used to produce independent reference
values remain distinct from application runtime dependencies.

## 🛠️ Final activities

1. Obtain owner acceptance of the candidate qualified in v0.9.0, confirming
   its scope and remaining limitations.
2. Confirm model, API, and export-format versions, with instructions for
   any supported incompatibility handling or migration.
3. Prepare release notes, instructions, and examples consistent with the
   final source and the behavior actually tested.
4. Follow RELEASING.md: version preparation, checks, authorized integration,
   certification of the final commit, an annotated tag, and publication
   when explicitly requested.
5. Deliver only artifacts built from the certified source and tested,
   with recorded hashes, and complete post-publication checks.

## 🔎 Practical example

A user follows the installation guide, opens the distributed workbook,
and reproduces a complete synthetic example. Results match the published
evidence within the stated tolerances. Source identity, model version,
configuration, and artifact hash identify the exact product used and
support reproducible defect reports.

## 🔗 Dependencies

[v0.9.0](v0.9.0.md) must be qualified, with final checks tied to the exact
release commit. If preparation or integration changes source identity,
update evidence under the release procedure; a PASS from a different
candidate cannot simply be reused.

## ✅ Completion criteria

- Owner acceptance and authorization for the intended publication or
  distribution are recorded.
- The final commit satisfies required static checks, compilation, Excel
  tests, numerical references, and scenarios, with explicit limitations.
- Workbook and source correspond; build, test results, and hashes are
  documented.
- Release notes, installation instructions, examples, and contract versions
  accurately describe the delivered product.
- Authorized tags, releases, and artifacts follow RELEASING.md, and
  post-publication checks pass. A published artifact is not silently
  replaced, and a tag is not moved.

## 🚧 Meaning of “validated” and scope boundaries

The term refers to the checks defined for this project, scope, source,
and documented environments. It does not mean regulatory approval or
replace the internal validation a bank requires for its own use.
The application does not automatically include a full banking-book EVE/NII
engine; that extension requires separately approved scope.

A milestone named v1.0.0 does not independently authorize publication,
distribution, or a visibility change. Creating this guide performs none
of those actions.
