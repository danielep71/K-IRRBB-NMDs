# ⚖️ v0.7.0 — Scenarios and regulatory overlays

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/K-IRRBB-NMDs/milestone/7) · [Previous](v0.6.0.md) · [Next →](v0.8.0.md)

## 🎯 Objective

Deliver coherent rate scenarios and source-traceable regulatory constraints,
applied in a separate layer that never rewrites the econometric estimates.

**Why it matters.** A duration estimated from data does not establish that
the same duration is permitted under a particular regulatory framework, and
even a correctly transcribed rule can be used in the wrong context. Each
rule's source, version, applicability and category mapping must be known
before it is applied, and its effect on the result must be observable.

## 📦 Scope

- Complete official-source verification and applicability decisions in #35
  using BIS, EBA and EUR-Lex texts: document, version, exact location, access
  evidence and basis for applicability; unverified rules stay explicitly
  provisional or unsupported.
- Define and record baseline and configured rate paths by currency, origin
  and horizon; transmit them to Rates and Stable through the dependencies
  accepted in v0.6.0, never giving Decay a rate input its contract lacks.
- Verify supervisory scenarios, currency-specific parameters and floors where
  applicable.
- Select the regulatory framework explicitly and map regulatory deposit
  categories to data segments, with core/non-core treatment, time allocation
  and repricing constraints.
- Apply constraints in a separate layer, retaining the statistical profile,
  the constrained profile and the reconciliation of the difference; review the
  decay prototype's `REG-1` overlay against this layer.
- Reconcile the remaining obligations of #26 with evidence; creating child
  issues alone does not complete them.

## 🏁 Exit criteria

- [ ] Every applied rule cites an accessible official source, exact location,
  version and documented applicability; unverified rules are labelled
  provisional or unsupported.
- [ ] Scenarios, currency-specific parameters and constraints have
  independent cases with recorded results and tolerances.
- [ ] Unconstrained and constrained results are reported separately and
  reconcile, without changing the original fit.
- [ ] An unverified required parameter never yields an outcome presented as
  validated or compliant.
- [ ] Unconstrained results from v0.3.0–v0.6.0 are unchanged.
- [ ] Coordinated execution and failure cases run on Windows 64-bit Excel on
  the exact commit.
- [ ] README, CHANGELOG, `SOURCES.md`, `MODEL_CONTRACTS.md` and this guide
  state the verified rules, selected framework and remaining exclusions.

**Example acceptance case.** A synthetic case starts with a statistical
profile and selects a framework for which a particular rule has been verified
and found applicable. The output shows the original profile, the
transformation, the final profile and the reconciliation of amounts, with
values from an independent reference. If a required parameter remains
unverified, the outcome is not presented as validated or compliant.

## 🚫 Not in scope

A full banking-book EVE/NII engine and any claim of universal regulatory
compliance. This guide does not verify or update regulations or numerical
limits; their authoritative status is in the
[source register](../methodology/SOURCES.md).

## 🧪 Release evidence

- Pass `python tools/check.py --ci` and the hosted Repository integrity check
  on the exact candidate.
- Record Windows Excel 64-bit stages 1–6 of
  [`EXCEL_EVIDENCE.md`](../EXCEL_EVIDENCE.md), the scenario, constraint,
  reconciliation and failure cases.
- Record independent numerical references and the source register entries for
  every applied rule, with reviewer, tolerance and limitations.
- Record the candidate SHA, the source round trip, limitations and
  documentation updates.
- Do not tag, publish or merge to `main` without explicit owner authorization.
